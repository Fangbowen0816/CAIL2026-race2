# 技术方案 · CAIL 2026 赛道三「智能合同审查」

> 定稿：2026-11-14 ｜ 当前进度见文末「状态」

## 1. 目标与约束

- **输入**：`contracts.jsonl`，每行 `{contract_id, context}`，`context` 用 `<p id="N">正文</p>` 标注段落（初赛 15 份，44–175 段）。
- **输出**：zip 内固定两份 JSONL —— `localization_predictions.jsonl`、`revision_predictions.jsonl`。
- **评分**（官方）：
  - 定位 `L = 10·F_typo + 30·F_inconsistency + 60·F_missing`（**权重 1:3:6**）
  - 修订 `R = 10·T + 30·C + 60·M`
  - 总分 `S = 0.5·L + 0.5·R`
- **晋级线**：初赛超官方基线 Qwen3.8-27B **总分 25.09**。
- **阶段权重**：最终 = 初赛 10% + 复赛 30% + 封测 60%。
- **封测硬约束**：单条 HTTP 请求；**幂等 + 无状态**；超时 600s。
- **时钟**：初赛窗口 2026.10.15–11.15（**明天截止**）。

## 2. 架构决策（ADR）

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 控制流 | **单层确定性 workflow**（固定 DAG） | 控制流已知；任务为结构化预测；LLM 编排只增非确定性与不可复现 |
| 是否分层 agent/subagent | **否**，删除 | 层间序列化/误差放大/状态归属/可观测性成本 > 收益 |
| 可扩展性来源 | **Stage 接口**，非 agent 抽象 | 将来复杂节点换 ReAct，只换该阶段实现，骨架不动 |
| 状态归属 | **唯一真相源 `ContractState`** | 避免副本漂移、陈旧读 |
| 阶段形态 | 纯函数 `run(view) -> typed_output`，orchestrator 合并、推进版本 | 每跳可校验、可重放 |

**升级触发条件**（满足任一才引入 ReAct / 多 agent）：出现必须多轮工具检索才能定的节点；或单节点失败率高到需自主探索重试。届时只替换该 `Stage` 实现，不改接口。

## 3. 数据流（S0–S5）

```
contracts.jsonl
 │
 ├─[S0 解析]     段落 → {pid: text}                              （确定性）
 ├─[S1 事实抽取] 正则抽取当事人/金额/日期/期限/数量/单价/比例
 │               每条 (类型, 值, 所在 pid 列表)                   （确定性）★关键
 ├─[S2 定位]     LLM：typo + missing_element（事实表作提示）
 │               LLM：inconsistency（事实表冲突对 → 确认/补全）
 │               → 规则合并去重 → LocalizationRecord[]            （LLM + 规则）
 ├─[S3 修订]     inconsistency：事实表定"取哪套值" → 一次修订并同步全部冲突段
 │               typo/missing：逐段修订为完整最终文本
 │               → RevisionRecord[]                              （LLM + 规则）
 ├─[S4 校验]     重抽事实表检查残余冲突/缺失；有则**限 1 次**回修
 │               （此环 = 未来 ReAct / 自检工具的接入点）          （确定性 + 限1次LLM）
 └─[S5 产出]     两份 JSONL + zip + 格式自检
```

**切分依据**：定位分中"不一致 + 缺失"占 90%，且二者是**全局约束**——用确定性事实表做交叉比对；LLM 只负责"语义改写"。实测短板正是 missing 的修订（11.6），prompt/逻辑问题，与是否 agent 无关。

**LLM 用量**：约 3 次/合同（定位 1–2 + 修订 1 + 可选回修 1），15 份成本极低。

## 4. 模块与接口

**已实现**：`contracts / records / llm / prompts / predictor / submission / pipeline / env`
`state / stage / stages / facts / verify`（M1）
`hints / detect / revise`（M2：Stage 流 facts→verify→detect(LLM)→revise(LLM)）。

**Stage 接口（已落地）**：

```python
@dataclass
class ContractState:          # 唯一真相源
    contract_id: str
    paragraphs: dict[int, str]        # 原始，不可变
    facts: list = field(default_factory=list)
    localizations: list = field(default_factory=list)
    revisions: list = field(default_factory=list)
    final_paragraphs: dict = field(default_factory=dict)
    version: int = 0

class Stage(Protocol):
    name: str
    def run(self, state: ContractState) -> ContractState: ...   # 返回新版本（增量合并）
```

- 阶段只读 `state`，产出 typed 增量；orchestrator（`pipeline.py`）按序调用、合并、bump `version`。
- 出参直接复用提交 schema（`records.py`），不引入第三套表示。
- 每跳：入/出参校验 + 失败策略（重试 → 降级到确定性兜底）。

**M2 一致性约束**：修订段 `error_types` 强制等于其 PID 的定位类型并集
（未定位却被修订则补定位），否则平台整体退回——已在 `revise.reconcile` 实现并自检为 0 ERROR。

## 5. 模型与服务

- 模型：`deepseek-v4.1-flash`，base_url `https://shared.kscc.api.ksyun.com/v1`，头 `ksyun-code-type: ksxc-cli`（缺则 403）。
- 配置全走环境变量（`CAIL_API_KEY/BASE_URL/MODEL/HEADERS`）；key 不进 repr/异常/日志，`.env` 已 gitignore。
- 幂等：temperature=0；同合同重复请求结果一致（为封测一致性抽查准备）。

## 6. 评测与验证

- **自检**：`scripts/validate_submission.py`（覆盖/唯一/区间/逐字一致/类型一致，exit 1 = ERROR）。
- **本地打分**：`scripts/eval_examples.py` —— 在 `提交示例/` 的 2 份 gold 上算 L/R/S。
  - 定位分按 1:3:6 **精确复现**；修改分为**近似口径**（官方脚本不公开）。
- **单测**：`pytest`，覆盖解析/不变量/协议映射/错误路径/原子写/评测函数。
- **局限**：15 份初赛合同**无 gold**，只能靠 2 份示例 + 线上榜分迭代。

## 7. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| missing_element 最重且最难 | 事实表 + 条款模板扫描；专项 prompt 迭代 |
| 无本地 gold，易过拟合 2 示例 | 用线上榜分做主信号；示例只做回归 |
| 封测幂等/在线 | temperature=0、无状态、健康检查 `/health` |
| 长合同漏检 | 事实表兜底；必要时分块+重叠 |
| 时间紧（明日截止） | 先出可提交版本，再迭代提分 |

## 8. 里程碑

- **M1**（现在）：`facts.py` / `verify.py` 落地 + 确定性单测。
- **M2**：`localize`/`revise` prompt 迭代，mini eval 提升 missing 修订分。
- **M3**：全量 15 份 → 自查 → 提交初赛。
- **M4**（复赛/封测）：按触发条件，择一节点换 ReAct（接口不变）。
